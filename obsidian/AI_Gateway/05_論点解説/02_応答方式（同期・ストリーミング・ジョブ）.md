# 02 応答方式 ── 返し方ひとつで、仕様と実装がどこまで変わるか

*個人検討ノートの一般化版（2026-11-16 同期・正は個人 Vault）*

> [!NOTE]
> **この解説が支える台帳の行**
> [論点台帳](../03_論点台帳.md) §3「応答方式（同期・ストリーミング・ジョブ）」。3方式の仕組みそのものの正典は [06_同期・ストリーミング・ジョブ](../90_基礎知識/04_同期・ストリーミング・ジョブ.md)（シーケンス図つき）。ここではそれを前提に、このプロジェクトに当てて「決めた瞬間に、仕様（契約）と実装（GW の作り）のどこが変わるか」を具体にする。Copilot 型の画面内アシスタントでは、押してから答えが見え始めるまでの体感が品質そのものなので、この論点の優先度は高い。

## 1. まず仕組み ── 3つの返し方

返し方は3方式あり、封筒（共通フォーマット）の `status` で区別される。

- **同期**：送って、待って、完成品を1回で受け取る。封筒は `status: "ok"` が1通。
- **ストリーミング**：できたそばから断片を流す。SSE（サーバから小さなメッセージを送り続ける仕組み）[^sse]などを使い、途中は `status: "partial"` を何通も、**最後の1通で `ok` と usage を確定**して閉じる。
- **ジョブ**：「受け付けました」とだけ即答し（`status: "accepted"`＋`job_id`）、フロントが後で結果を取りに来る。

それぞれの向き不向き・シーケンス・「同じ封筒で3方式を表す」勘所は正典に譲り、以下は影響範囲だけを掘る。

## 2. 仕様（契約）への影響 ── 封筒より先に握らないと作り直し

### 2.1 封筒の席が変わる

`status` の語彙（ok・partial・accepted・error）、`options.stream`、`job_id` は、返し方のための**予約席**である。同期前提で封筒を固めてから後で partial や `job_id` を足すと、フロントも GW も作り直しになる（→ 正典 §6-1）。台帳 §1「共通フォーマットは JSON でよいか」は、この予約席を最初から彫り込むかという問いと連動している。

### 2.2 usage の確定タイミングが変わる

同期なら応答と同時に usage（1件ぶんの消費量）が出る。ストリーミングでは**最後の1通まで確定しない**。ジョブでは完成時に出る。つまり「利用量を記録し、残枠と突き合わせる」処理の発火点が、方式によって移動する。失敗時も途中までの消費を返して帳簿に穴を開けない、という原則（→ [04_usageとトークン](../90_基礎知識/03_usageとトークン.md) §4-2）を守る形も、方式ごとに違ってくる。

### 2.3 エラーの表し方がひとつ増える

ストリーミングには「途中まで送った後に失敗する」という、同期には無い状態がある。partial を何通か送った後の error を統一エラー（→ 03_統一エラーモデル）でどう表すか、フロントは途中まで表示した文章をどう扱うか——契約に決めごとが1つ増える。

## 3. 実装への影響 ── GW の作りがどう変わるか

### 3.1 同期 ── いちばん簡単。主戦場はタイムアウト

実装は FastAPI のハンドラ1本で済み、歩く骨格（Phase 0）と同じ形のまま LLM の応答を待つだけである。設計の本体は「待ち時間」の側に移る。LLM は遅く、たまに失敗する前提なので、GW 自身のタイムアウト・リトライ（台帳 §3「遅さ・失敗への備え」）、経路上の httpd のタイムアウト設定との整合、そして「利用者は何秒まで待てるか」という要件を握ることが仕事になる。欠点は、長い生成で画面が無反応になることである。

### 3.2 ストリーミング ── GW が「素通しの中継管」になる

採用した瞬間、GW の性格が変わる。影響は4つある。

1. **判定は送信開始前に完済させる**。断片を流し始めてから「やっぱり権限なし」とは言えない。構成図の判定列（検証 → 通過可能 → 利用可能）は、最初の1バイトを返す前に終える前提になる。
2. **中継と変換が逐次になる**。GW は上流からの断片を受けては流す管になる。FastAPI 側はストリーミング応答の実装になり、データ形式変換（convertor）も一括処理でなく**断片単位の逐次変換**になる。
3. **経路の全部が「ためない」必要がある**。GW の WEB サーバや httpd（リバースプロキシ）が応答をためて（バッファして）から転送する設定だと、少しずつ返す意味が消える。httpd 側の設定確認が必須になる（具体の設定値は実装 Phase で一次情報とともに確定させる）。
4. **記録とログが完了時に寄る**。§2.2 のとおり usage は最後に確定するので、利用量の記録・残枠の消し込み・ログ出力は、ストリームの完了（または中断）時にまとめて行う作りになる。

### 3.3 ジョブ ── GW が「状態」を持ち始める

受理だけ即答して後で結果を渡すには、**`job_id` と結果の置き場**が要る。ここで記録DBの論点（→ [01_利用管理](./01_利用管理（使用制限・記録DB・仮想キー）.md)）と絡む。しかも保存する結果は本文そのものなので、「ログに本文を残さない」方針（台帳 §4）と正面からぶつかり、保持期限・取得できる人の制限・消し方という論点が派生する。さらに、受理後も処理を続ける仕組み（ワーカー）が要るため、GW は「呼ばれて返す関数」から「仕事を抱える常駐者」へ一歩踏み出す。実装の重さは3方式で最大である。

### 3.4 影響の一覧

| 方式 | 封筒（仕様） | GW実装 | httpd | 利用量・ログ | 実装の重さ |
|---|---|---|---|---|---|
| 同期 | ok を1通 | ハンドラ1本＋タイムアウト設計 | タイムアウトの整合 | 応答時に記録 | 小 |
| ストリーミング | partial 複数＋最後に ok・usage 確定 | 逐次中継・逐次変換・事前判定 | バッファさせない設定の確認 | 完了・中断時に記録 | 中 |
| ジョブ | accepted＋`job_id` → 後で ok | 結果の保管・ワーカー・取得口 | 特記なし | 完成時に記録＋保管の機密設計 | 大 |

## 4. この案件での決め方 ── 第一弾の返し方だけ先に握る

全部を今決める必要はない。正典の結論どおり、**封筒に3方式ぶんの席（`status` の語彙・`options.stream`・`job_id`）だけ最初から確保**しておき、**第一弾機能をどの方式で返すかだけ**を業務システム側（フロント）と握るのが安全である（→ 正典 §6-4）。Copilot 型の体感ならストリーミングが定番候補だが、歩く骨格（Phase 0〜1）は同期で立てておき、席を確保したまま後からストリーミングへ進む、という段階も取れる。どれを採るか（★）は台帳 §3 の行に記入する。
