# 06 LiteLLM 公式ベンチマーク（和訳）── 性能とサイジングの根拠資料

*個人検討ノートの一般化版（2026-11-18 同期・正は個人 Vault）*

> [!NOTE]
> **この資料の位置づけ**
> LiteLLM 公式の性能試験結果（Benchmarks ページ）を**日本語で紹介するための資料**。数値・条件はすべて公式ページの記載を和訳したもので、独自の測定・推定は「読み方」の節に分けて明示する。[論点台帳](../03_論点台帳.md) §3「性能規模」「Redisをいつ入れるか」の根拠資料であり、複数インスタンス構成の絵は [構成図v3](../02_構成図/v3_複数インスタンス.md)。

## 1. 試験①：高スループット（重量級プロンプト・5万〜10万トークン）

**毎分135億トークン（13.5 billion TPM）・毎秒3,000リクエストを処理**した試験。入力が非常に大きい（5万〜10万トークン）条件での上限性能を示す。

| 指標 | 結果 |
|---|---:|
| 毎秒リクエスト数（RPS） | 3,000 |
| クライアント側 HTTP 200 率 | 100.00% |
| ゲートウェイ処理遅延 p50 | 30.581 ms |
| ゲートウェイ処理遅延 p95 | 54.029 ms |
| ゲートウェイ処理遅延 p99 | 91.645 ms |
| 最初のトークンまでの時間 p50 | 31.667 ms |

試験条件（和訳）：

| 項目 | 内容 |
|---|---|
| 構成 | **ゲートウェイ33ポッド**。各ポッド＝4ワーカー・4vCPU・メモリ16GiB |
| 負荷 | 分散 Locust（負荷生成30ワーカー）。3,000ユーザーが各毎秒1リクエスト |
| リクエスト | `/v1/chat/completions`。5万・7.5万・10万トークンのプロンプトを等分、50%はストリーミング、`max_tokens: 16` |
| モデルと経路 | プロセス内モックモデル。AWS の ALB 経由。クライアントタイムアウト60秒 |
| 有効機能 | PostgreSQL と Redis・仮想キー予算・トークンカウント・spend 追跡・メトリクス（応答キャッシュは無効） |
| 時間 | 24分22秒 |

## 2. 試験②：Realtime API（WebSocket）

**毎秒1,207リクエスト**。常時接続（WebSocket）での性能を示す。

| 指標 | 結果 |
|---|---:|
| エンドツーエンド遅延 p50 | 59 ms |
| 同 p95 | 67 ms |
| 同 p99 | 99 ms |
| 同 平均 | 63 ms |

試験条件（和訳）：**4インスタンス**（各4ワーカー・4vCPU・8GB RAM）／Locust 1,000ユーザー（リクエスト間0.5〜1秒）／`/v1/realtime` を持続的 WebSocket で・モックエンドポイント／PostgreSQL あり・**Redis 無効**。

## 3. 試験③：短文チャット（軽量プロンプト）

**4インスタンスで毎秒1,170リクエスト・ゲートウェイ上乗せ遅延 p95＝8ms**。もっとも軽い条件で、インスタンス数との関係が読める試験。

| 指標 | 2インスタンス | 4インスタンス |
|---|---:|---:|
| 毎秒リクエスト数（RPS） | **1,035.7** | **1,170** |
| リクエスト遅延 p50 | 200 ms | 100 ms |
| 同 p95 | 630 ms | 150 ms |
| 同 p99 | 1,200 ms | 240 ms |
| 同 平均 | 262.46 ms | 111.73 ms |
| ゲートウェイ上乗せ p50 | 12 ms | 2 ms |
| 同 p95 | 29 ms | 8 ms |
| 同 p99 | 43 ms | 13 ms |
| 同 平均 | 14.74 ms | 3.32 ms |

試験条件（和訳）：各インスタンス4vCPU・8GB RAM（4インスタンス試験は各4ワーカー。2インスタンス試験のワーカー数は記録なし）／Locust 1,000ユーザー（リクエスト間0.5〜1秒）／`/chat/completions` にランダムID付き短文×150反復／モック OpenAI エンドポイント／PostgreSQL あり・**Redis 無効**。

## 4. 試験④：ログ連携のオーバーヘッド

外部ログ連携を足しても性能がほぼ落ちないことを示す試験（構成の詳細は公式に記録なし）。

| 構成 | RPS | 遅延中央値 |
|---|---:|---:|
| 素のプロキシ | 1,133.2 | 140 ms |
| GCS バケットへのログ | 1,137.3 | 138 ms |
| LangSmith へのログ | 1,135 | 132 ms |

## 5. 読み方（含意）── ここからは本資料の解釈

数値そのものは上の公式記載がすべてで、以下は**サイジング検討のための読み下し**である。

1. **プロンプトの重さで1台あたりの処理能力が1桁変わる**。短文なら2台で約1,036 RPS（≒約518 RPS/インスタンス）、重量級（5万〜10万トークン）では約90 RPS/ポッド（3,000÷33）。長文・画像（base64で入力が膨らむ）を扱う計画なら、重い側の数字で見積もる。
2. **ゲートウェイ自体の上乗せは小さい**（短文 p95 で 8ms・重量級 p95 でも 54ms）。遅延の大半は LLM 側で生じる＝プロキシ層がボトルネックになるのは相当な高負荷から。
3. **約1000 RPS は、最軽量条件でも2インスタンス**が公式実測。単一の大型サーバー（例：64コア）でも、1プロセスではCPUを使い切れないため多ワーカー／多コンテナ化が必要で、公式の線引き「**ワーカープロセスが2つ以上なら Redis**」に掛かる（[論点台帳](../03_論点台帳.md) §3・[構成図v3](../02_構成図/v3_複数インスタンス.md)）。
4. **モック測定である点に注意**。実モデルでは上流（LLM 側）のレートと遅延が先に効くので、これらの数字は「プロキシ層の上限の目安」として読む。本番の台数は、実プロンプト・実ピークの測定で決める（公式のサイジング手引き＝Sizing & Scaling／Autoscaling／Database Sizing）。
