# 手順書（LiteLLM_x4 ── litellm×4＋内部LB＋Redis）

このフォルダ単体で、gateway・web・litellm×4・litellm-lb・db・redis を起動し、LLMプロバイダとの疎通確認まで行う。プロバイダは入れ替え可能で、この手順書では Vertex AI を既定の例として示す。

## 1. 前提

Docker Engine と Docker Compose が使えること。次のコマンドでバージョンが表示されることを確認する。

```bash
docker compose version
```

## 2. 配置

このフォルダ（`LiteLLM_x4`）を丸ごと任意の場所へコピーする。以降のコマンドはすべて、コピーしたフォルダの直下で実行する。

## 3. .env の作成

```bash
cp .env.example .env
```

作成した `.env` と関連ファイルを、次の「書き換えが必要」「好みに応じて変えてよい」の2節に従って編集する。

### 書き換えが必要（使う LLM プロバイダの接続情報）

書き換えが必須なのは、使う LLM プロバイダの接続情報だけ（本体が依存する秘密は `.env` と `secrets/` のファイルのみ）。

**既定の例＝Vertex AI の場合**

| ファイル | 箇所 | やること |
|---|---|---|
| `.env` | `VERTEX_PROJECT` | 使用する GCP プロジェクト ID に書き換える |
| `.env` | `GOOGLE_APPLICATION_CREDENTIALS` | 手順7で `secrets/` に置く認証JSONのファイル名に合わせる（`/secrets/<ファイル名>`）。ADC の既定名 `application_default_credentials.json` を使うならそのままでよい |

**他プロバイダ（例: OpenAI）の場合**

| ファイル | 箇所 | やること |
|---|---|---|
| `.env` | プロバイダのキー（例 `OPENAI_API_KEY`） | 使うプロバイダのキーを設定する（Vertex 用の上の2行は使わない） |
| `litellm_config.yaml` | `model_list` | そのプロバイダのモデルに差し替える（compose・コードは無改修） |

### 好みに応じて変えてよい（変えなくても動く）

| ファイル | 箇所 | やること |
|---|---|---|
| `.env` | `LITELLM_MASTER_KEY`・`LITELLM_SALT_KEY`・`LITELLM_VIRTUAL_KEY` | ダミーキーを任意の値に変える（`LITELLM_SALT_KEY` は初回起動後は変えない） |
| `.env` | `POSTGRES_PASSWORD` と `DATABASE_URL` のパスワード部 | 2か所を同じ値に揃えて変える |
| `litellm_config.yaml` | `model_list` の `model` | 使う実モデル名に変える |
| `compose.yaml` | 各サービスの `ports` の左側（8000・5000・4000） | ホスト側の公開ポートを変える |
| `compose.yaml`・`litellm_lb.conf` | `litellm-N` サービスと `upstream` の `server` 行 | インスタンス台数を増減する（compose の `litellm-N`・gateway の `depends_on`・`litellm_lb.conf` の `server` 行を同数に揃える） |

## 4. 起動

```bash
docker compose up -d --build
```

## 5. 起動確認

```bash
docker compose ps
```

次の状態になっていることを確認する。

| サービス | 期待する STATUS |
|---|---|
| db・redis・litellm-1・litellm-2・litellm-3・litellm-4 | `Up (healthy)` |
| gateway・web・litellm-lb | `Up` |

## 6. 疎通確認（コンテナ間・ホスト）

コンテナ間（gateway → litellm-lb）。

```bash
docker compose exec gateway curl http://litellm-lb:4000/health/liveliness
```

`"I'm alive!"` が返ることを確認する。

ホストから litellm-lb。

```bash
curl http://localhost:4000/health/liveliness
```

`"I'm alive!"` が返ることを確認する。

ホストからモデル一覧（`.env` の `LITELLM_MASTER_KEY` を変えた場合は Bearer の値を合わせる）。

```bash
curl -H "Authorization: Bearer sk-dummy-master-key-0000" http://localhost:4000/v1/models
```

`"id": "gemini"` を含む JSON が返ることを確認する。

ホストから gateway。

```bash
curl http://localhost:8000/healthz
```

`{"status":"ok"}` が返ることを確認する。

ブラウザで `http://localhost:5000` を開き、入力欄・利用者IDと仮想キーの入力欄・同時リクエスト数・「AIに送る」ボタンのある画面が表示されることを確認する。

## 7. LLMプロバイダ疎通確認

### 共通の確認（どのプロバイダでも同じ）

使う LLM プロバイダの資格情報を設定する（やり方は下の「Vertex AI の場合」「他プロバイダの場合」）。設定したら litellm を再起動する。

```bash
docker compose restart litellm-1 litellm-2 litellm-3 litellm-4
```

ブラウザで `http://localhost:5000` を開き「AIに送る」を押す。または次のコマンドで1往復させる。

```bash
curl -i -X POST http://localhost:8000/api/chat -H "Content-Type: application/json" -d '{"message":"1文で自己紹介して。"}'
```

HTTP 200 と AI の応答本文が返ることを確認する。資格情報が未設定のまま送ると、プロバイダ段のエラーが返る（Vertex AI なら `/secrets/... not found` を含むエラー）。これは「経路が認証の手前まで通っている」目印で、どのプロバイダでも同じ見方ができる。

任意の追加確認として、仮想キー欄に誤ったキー（例 `sk-wrong`）を入れて送ると `401 Authentication Error` が返ることを確認する（キーが台帳と照合されている目印）。

### Vertex AI の場合（既定の例）

認証JSON（サービスアカウント鍵 または ADC）を `secrets/` に置き、`.env` の `GOOGLE_APPLICATION_CREDENTIALS` が、置いたファイル名（`/secrets/<ファイル名>`）と一致していることを確認する。

鍵JSONが手元に無い場合だけ、任意の補助として次のコマンドで ADC を作成できる（表示された URL をブラウザで開いて認証すると `secrets/application_default_credentials.json` ができる）。この gcloud サービスは Vertex 専用の補助で、使わなくても・compose から消しても本体には影響しない。

```bash
docker compose run --rm gcloud
```

### 他プロバイダ（例: OpenAI）の場合

`.env` にそのプロバイダのキー（例 `OPENAI_API_KEY`）を設定し、`litellm_config.yaml` の `model_list` をそのプロバイダのモデルに差し替える（compose・コードは無改修）。そのうえで、上の「共通の確認」を同じ手順で行う。

## 8. 停止・撤去

```bash
docker compose down
```

`-v` を付けると DB（発行済みキー等の台帳）も消えるので注意。
